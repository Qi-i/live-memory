# Live Memory V3：底层、同步、Web/Android 和视觉系统重构基线

**状态：目标架构与执行约束；本分支不直接发布。**  
**基线：2026-11-08 main 249f77cf。**

本文件不是换肤方案，也不是逐张截图修补清单。旧系统在迁移期间保持稳定，所有真实记录、图片与云端账号数据必须可备份、可核验、可回退。

## 一、结构性问题与架构目标

当前 appController.ts 同时管理数据库、云端恢复、媒体续签、页面路由、编辑、用户通知；supabase.ts 同时管理认证、文字备份、图片上传、合并、冲突与账号状态。业务决策直接耦合网络请求和 React 组件，因此旧问题跨页面反复出现。

同一记录的 updatedAt / syncedAt 只能证明时间顺序，不能可靠证明两端从同一版本并发修改。无条件显示“恢复成功”的提示、旧异步同步结果整体覆盖新编辑、账号云与个人云共享模糊的时间基线，都是这一问题的不同表现。

档案、分享、地图、编辑界面由超大型 TSX 文件与多份按时间追加的 CSS 决定，缺乏统一的布局坐标系和交互状态机；这些问题不能通过继续增加覆盖样式消除。

**目标：以统一领域模型、操作协议、应用状态、UI 布局系统和平台适配层代替上述耦合。**

## 二、新架构的分层和依赖约束

| Ports | RecordRepository、CloudSyncAdapter、MediaRepository 接口 | src/core/ports/ |

## 三、同步协议 V3

版本身份由 recordId、accountScope、providerId 和 acknowledgedRevision 共同确定。acknowledgedRevision 是云端已确认内容的 SHA-256 摘要；不能用本机点击保存时的当前时刻冒充远端确认，也不能混用账号文字备份与个人云的版本基线。

三方判断：

1. 本机和云端的语义内容相同：无变化。图片签名 URL、来源标签和同步时间变化不算用户编辑。
2. 本机偏离共同基线、云端未变：正常本机更新，进入上传队列，不弹冲突。
3. 云端偏离共同基线、本机未变：正常远端更新，进入下载合并，不弹冲突。
4. 双方均从共同基线发生不同内容变化：真实并发。优先检查字段级是否可安全合并；冲突不可自动无声覆盖。
5. 旧档案尚无可验证共同基线：进入兼容迁移流程。禁止简单地根据时间戳选一端覆盖，也不能把未知历史误判为真正的冲突。
6. 删除必须依靠删除命令或墓碑。远端某次响应缺少一条记录，并不等于要删除本机内容。

每次同步捕获账户身份和请求开始时的记录版本。响应返回后必须重新读取本机当前内容，逐条判断是否仍然可以应用；不能对整库 clear/put。需要通过服务器端条件更新（CAS 或版本 RPC）保证两个设备不会因普通 upsert 抢写而丢失修改。账号云仅作认证及可选文字灾备，私人云为完整媒体/文字同步源，二者不能互相重置对方的确认基线。

首次迁移须先生成可验证的完整备份，建立只读对账，成功后再初始化共同版本。新版本元数据先放在旁路空间，保持 EventRecord 现行格式可读。不允许未经验证直接启动新的远端写入。

状态事件由统一状态机发布：idle、checking、connected、transferred、conflict、offline、error。正常连接、零变化查询与自动恢复静默；只有确实新合并的数据进入历史状态中心；真正冲突及必要错误才需要显式提醒。

## 四、完整 UI 空间体系

**AppShell** 负责左导航、顶部全局工具条、主内容滚动区域及系统级 OverlayHost 四个明确的空间层。同步和导入消息放在导航留白处的 StatusCenter，或顶部状态入口展开，不允许在主页面文档流中插入高度不稳定的提示横条。页面内容不可因普通同步改变坐标。

**演出海报** 使用统一 PortraitArtwork 原语，维持海报原始比例。首页 Banner 必须先保证竖向海报完整可辨认，再决定高度和布局；不同宽度切换横向海报画廊、栅格或轮播。禁止为了在一行装五张而把竖图变成扁条。分享图使用独立布局服务，但读取同一媒体缓存。

**城市/场馆** 是一个固定视觉边界的地图与排名复合面板：地图与右侧列表齐高，双方各自的滚动职责明确，底部不留无意义空白；地图标记点击显示受地图可视区域约束的详情浮层，竖版海报不压扁。移动端改成底部抽屉，不简单把桌面浮窗缩小。

**汇总工具栏** 按主次信息分组。空间不足时次级操作折叠到“更多”，不能让高频按钮裁切到窗口外，也不以缩小字号代替合理布局。筛选、排序和导出在每个视图拥有一致的操作位置。

**编辑与弹层** 统一“草稿→校验→保存中→成功/失败”状态，不允许关闭中断保存而丢失数据。详情/图片/编辑/导入/分享和冲突都由 OverlayHost 管理层级、Esc、焦点和滚动。不能为每个弹窗另造状态逻辑。

**视觉系统** 使用语义 design tokens 统一排版、间距、颜色、玻璃透明度、动效、层级和容器，支持 Liquid Stage 与无玻璃的 Editorial。玻璃材质用于大模块和导航，不对海报墙逐卡做高成本模糊。历史 Hotfix 类样式必须逐步迁出，禁止新增时间戳覆盖层。

断点按行为规划：360、390（Android）、768（平板）、1024/1280（笔记本）、1600/1920（桌面）；同时验证文字缩放、旋转、低性能设备、失焦返回和离线重开。每个尺寸需要独立的布局决策，不能默认所有桌面控件都在手机上显示。

## 五、自动化验收门槛

必须使用空档案、35 场、200 场、缺海报、极长标题、20 城市、多媒体、不同账号与低网速覆盖测试。每种关键页面用浏览器实际测量可见元素尺寸并截图核验，而不只检查 CSS 字符串。

强制同步用例：正常单设备编辑不产生冲突；双端真正并发才产生冲突；本机在请求等待期间编辑不能被覆盖；账号与个人云各自建立版本；图片 URL 续签不算内容修改；网络恢复无重复成功横幅；墓碑不复活；断网和账号切换不混数据。

强制 UI 用例：恢复通知不引起主内容位移；Banner 原图比例可辨；地图/右列等高且详情弹层按钮完整可达；汇总操作不裁切；二级弹层不出现滚动冲突；手机端能完成新增、编辑、保存、查看和分享。

**发布原则：** 新内核先在独立分支与演示数据上运行，对照旧实现验证。只读对账、数据备份和回滚演练均通过，才允许对真实账号的写入通道逐步切换；每轮合并需 CI、浏览器视觉测试和数据不丢失证明。

## 六、已创建的基础与下一段任务

本分支实际建立：
- src/core/sync/revision.ts：语义快照和 SHA-256 版本；
- src/core/sync/policy.ts：三方版本决策和状态事件分级；
- src/core/sync/applyRemote.ts：对照真实本机最新状态筛除陈旧网络覆盖；
- src/core/sync/baselines.ts：按账户和提供方隔离持久化版本摘要；
- scripts/core-v3-contract-tests.mjs：版本、误冲突、陈旧响应、重复通知和身份隔离测试。

**这些基础模块尚未替换正式同步流程，不能宣称用户看到的恢复弹窗或误冲突已经修好。** 下一步需要原子 RecordRepository、远端 CAS、旧账号基线初始化与真实双端对账；之后再将页面转到新的 AppShell/StatusCenter，替换旧页而非叠 CSS。

任何跳过数据保护、仅改截图或在未验证情况下直接覆盖主分支的操作，都不属于本次重构。


### 本分支新增的运行路径（演示适配器验证）

- src/core/ports/RecordRepository.ts：本机记录读写和按修订条件提交的统一接口。
- src/infrastructure/indexedDb/recordRepository.ts：在既有账户命名空间中以一个读写事务完成 getAll → 核对请求快照 → 条件 put；不再使用 clear/整库覆盖。
- src/core/ports/CloudRecordAdapter.ts：规定远端须返回服务器端不透明版本号，且全部写入必须携带 expectedRevision；禁止无条件 upsert。
- src/core/application/synchronizeRecords.ts：纯服务层编排快照、版本决策、重读本机、CAS、增量入库和确认基线；与 React 和 Supabase 实现解耦。
- scripts/core-v3-orchestration-tests.mjs：模拟双设备正常编辑、双端并发、网络中编辑、服务器条件写入失败、账号隔离以及无基线的旧档案。

这里使用的 CloudRecordAdapter 是**接口**；现有个人 Supabase 后端仍没有对应的原子 CAS 适配器。既然服务端没有可靠的条件写入，新流程就不能在真实账号上贸然启用。因此当前分支是基础性、可验证的重构工程，而不是生产迁移。

下一步除服务端 CAS 外，还应在 CI 构建隔离的双设备 Playwright 会话，使用临时 Supabase 测试项目检查同 ID 修改、图片墓碑和断网恢复，不得让自动测试写入用户的正式云库。
